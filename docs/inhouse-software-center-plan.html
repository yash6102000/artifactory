🛒 In-House Software Center — Custom Catalog + Santa Enforcement

Our own catalog + client app, built in-house • Santa (free, OSS, already Apple-approved) handles enforcement • No paid MDM, no vendor free tier • The Software Center is the ONLY way to get software — nothing else installs or runs • Mac first

THE CORE IDEA — OUR OWN CATALOG, PROVEN ENFORCEMENT
⚠️ Why we're doing this now
An employee downloaded and tried to crack a paid app on their company Mac. No admin restrictions exist today, so nothing stopped it — the vendor's anti-piracy check flagged it and a legal notice landed. macOS Gatekeeper only warns, it doesn't block; the first time IT learned what was installed was from an outside party, not internally. At 60 people and growing, that gap is bigger than one incident.
🎯 The goal, stated plainly
Every Mac gets software from our own catalog app — full stop. If it isn't in the catalog, it doesn't run. Not a policy people are asked to follow — enforced by the machine itself refusing to execute anything that wasn't packaged and signed off through our catalog.
Two pieces: one we build, one we reuse deliberately
The catalog + client app is ours — our branding, our approval flow, our UI, built in-house. The enforcement is Santa — free, open-source, and already approved by Apple for the exact capability we need (blocking unapproved execution). Writing our own enforcement engine would mean applying to Apple ourselves for a restricted entitlement with no guaranteed outcome, then maintaining kernel-adjacent code forever. Santa already cleared that bar years ago, at other companies' expense, not ours.

THE SOLUTION — WHAT WE BUILD, WHAT WE REUSE
Four components we build, one proven tool we reuse for the highest-risk piece
Everything employee-facing and everything IT-facing is ours. The one piece that runs on every process launch on every machine, with zero tolerance for bugs, is Santa — not because we can't write code, but because reusing years of production hardening there is the responsible call.
ComponentWhat it doesBuilt by
Catalog backendStores approved installers + metadata (name, version, icon, category), serves the catalog to clients via an APIUs
Admin consoleWeb UI for IT to upload a new package, approve a version, view install stats, review audit logs and exception requestsUs
macOS client appThe employee-facing catalog UI — browse, click Install, see progress and updatesUs (native Swift/SwiftUI)
Privileged install helperInstalls need admin rights — a signed helper does the install safely without handing the whole app root accessUs
Enforcement engineBlocks any app from running unless it matches something our catalog approved — the actual "outside not allowed" gateSanta (free, OSS)
✅ Why Santa specifically, and why it's safe to run on every machine
Built on Apple's modern Endpoint Security Framework, not the deprecated kernel-extension approach. Already carries Apple's approval for the exact restricted capability we need — no entitlement application, no waiting on Apple, no risk of denial. Open source and auditable — we can read every line before it ships. Nothing it logs leaves our infrastructure; rules and events sync to a server we run. Originally built and proven internally at Google's own scale before going public, and in production at many companies since. Fail-open/fail-closed behavior is configurable, so a Santa bug doesn't have to mean bricked laptops.
What it enforcesProtects againstHow

The one config that ties our catalog and Santa together

<key>BannedBlockMessage</key><string>Not approved. Get it from our Software Center.</string>
<key>EventDetailURL</key><string>https://software.internal.company.com</string>
Santa's block dialog points straight at our own catalog app — the two feel like one product to the employee, even though only one of them is code we wrote.
⚠️ The trade-off, stated honestly
Going straight to default-deny means anything not yet in the catalog breaks the first time someone tries it — including everyday dev tooling. That's why the build plan includes a short Monitor-mode burn-in and compiler/package rules before flipping enforcement on, and why the exception workflow is a same-day fix, not a queue.
TECH STACK — BUILT FOR ~100 MACHINES, PROVEN ON 5-10 FIRST
Same architecture at 5 machines and at 100 — only the test cohort is small, not the design
Every choice below already holds at ~100 Macs without a rewrite. The pilot only limits how many real machines we point it at first, so we can catch mistakes cheaply before trusting it company-wide.

DISTRIBUTING THE CLIENT APP — SAME MECHANISM AT 5 OR 100 MACHINES
The first-install problem (getting the app onto a Mac that has nothing yet) is identical at any device count — it's a bootstrap script, run once per machine, either by hand or through whatever enrolls new laptops. What changes with scale is how many times we run it, not what it is.
StepHow
Sign & notarize the client appBuild a signed .pkg with our Apple Developer ID, run notarytool so Gatekeeper doesn't warn on first launch — the ordinary, fast, automated notarization process (not the restricted entitlement from the enforcement discussion)
Host the installerDrop the signed .pkg on the same server, behind the same TLS-protected URL as the catalog
Pilot (5-10 Macs): get it onto each machineSlack link + one-line instruction, or IT installs directly via Screen Sharing/Apple Remote Desktop — fine by hand at this count
Later (~100 Macs): same install, at scaleThe identical signed .pkg, run through whatever onboards a new laptop (a setup script during device provisioning, or pushed as one task via Santa's existing Configuration-Profile delivery once that's live) — no new install mechanism to design
Confirm it's workingEach Mac shows up in the admin console's device list after first launch, at either scale
⚠️ What the pilot is actually for, given the stack is already sized for ~100
Since the architecture doesn't change between 5 and 100 machines, the pilot's job isn't "prove the stack scales" — it's catching real bugs (a bad package, a wrong Santa rule, a broken install flow) on a small blast radius before every laptop in the company depends on it.

📊 For context — the cost this replaces, and the cost this avoids
A paid MDM (Jamf/Kandji/Mosyle beyond its free cap) runs ~$8-12/device/month — ~$500-720/month at 60 devices. A fully custom enforcement engine (writing our own instead of using Santa) would have added an Apple approval dependency with no guaranteed timeline, plus a specialized security-engineering hire and indefinite per-macOS-version maintenance — this plan avoids all of that by reusing Santa for the one piece where reinventing it buys nothing but risk.
