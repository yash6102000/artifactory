📦 In-House Artifactory — Secure Package Registry Architecture

A pluggable, self-hosted package registry • Proxy + cache + vulnerability gate for npm, PyPI, Maven, Docker • Free/OSS-first stack • Build once, every team pulls from here

THE CORE IDEA — REGISTRY SHELL + PLUGGABLE SECURITY GATE
Build the registry proxy ONCE. Swap the vulnerability policy via config.
The registry shell (dev request → cache lookup → upstream fetch → local store → serve) is generic infrastructure. What counts as "allowed" — which CVE severities are blocked, which licenses are banned, which package names are quarantined — is defined by a ScanPolicy config. Deploy the same internal registry with different policies per team or per package ecosystem (npm, PyPI, Docker) and everyone still installs with a normal npm install, they just never see a vulnerable version.

MODULAR DESIGN — THE INTERFACE CONTRACT
Every scanner implements one interface: ScanProvider
The registry shell doesn't know or care which scanner is behind it. It sends a package name + version in, gets an allow/block/quarantine decision out. The scanner handles its own CVE database lookups, license checks, and malicious-package heuristics internally.
SCAN PROVIDER INTERFACE (TypeScript)
interface ScanProvider {
  // Core: check one package version, get a verdict
  scan(pkg: PackageRef): Promise<ScanResult>;

  // Optional: called once when a new version is first cached
  onFirstFetch?(pkg: PackageRef): Promise<void>;

  // Optional: periodic re-scan of already-cached versions
  onRescan?(pkg: PackageRef): Promise<void>;

  // Optional: human override / exception request path
  requestException?(pkg: PackageRef, reason: string): Promise<void>;

  // Optional: expose the policy this scanner is enforcing
  getPolicy?(): ScanPolicy;
}
MODE A: GATE-ON-CACHE
Scan Before First Serve
When the registry fetches a package version from upstream for the first time, it scans it synchronously before caching + serving it to the requesting dev. Strongest guarantee, adds latency on cache-miss only.
Use when: You want zero window where a vulnerable version could reach a developer, even once.
// Registry hook, npm example
onUpstreamFetch(async (pkg) => {
  const result = await scanner.scan(pkg);
  if (result.verdict === 'block') throw new RegistryError(403);
  return cacheAndServe(pkg);
});
MODE B: SCHEDULED SWEEP
Async Rescan + Retroactive Block
A nightly CI job re-scans every cached version against updated CVE feeds (new CVEs get published for old packages constantly). Anything newly flagged is quarantined and a Slack alert fires to whoever's project uses it.
Use when: Protecting against CVEs disclosed after a package was already cached and in use.
// cron: 0 3 * * * (nightly)
for (const pkg of registry.listCached()) {
  const r = await scanner.scan(pkg);
  if (r.verdict === 'block') registry.quarantine(pkg, r);
}
ScanResult — What Every Scanner Returns, Regardless of Backend
interface ScanResult {
  verdict: 'allow' | 'block' | 'warn';   // gate decision
  severity?: 'critical' | 'high' | 'medium' | 'low';
  cveIds: string[];                // e.g. ["CVE-2024-XXXX"]
  license?: string;              // detected license
  scannedAt: string;             // ISO timestamp
  source: 'trivy' | 'grype' | 'osv' | 'npm-audit';
}
REGISTRY OPTIONS — FREE / OSS-FIRST STACK
Given ~60 people and npm-first, Verdaccio is the fastest starting point
Nexus OSS is the better long-term pick if you'll eventually need Maven, PyPI, or Docker in the same place. GitHub Packages costs nothing but hands you less scanning control. All three sit behind the same ScanProvider interface, so the choice isn't permanent.

🔧 Verdaccio (recommended start)
  • Docker one-liner to run, config is a single YAML file
  • Proxies any npm scope to registry.npmjs.org, caches locally
  • Built-in web UI for browsing cached/published packages
  • Plugin system for auth (htpasswd, LDAP, custom)
📦 Nexus OSS (grow into)
  • One instance, multiple repo types (npm-proxy, pypi-proxy, docker-hosted)
  • Blob store for caching, cleanup policies for old versions
  • REST API to script blocking/quarantine after a scan hit
  • Heavier resource footprint (JVM), needs its own box/VM
☁️ GitHub Packages (zero-infra)
  • No server to maintain, uses existing GitHub org/permissions
  • Dependabot alerts give some free vulnerability visibility
  • Less control over "hard block" policy vs. warn-only
  • Good fallback if nobody wants to own registry uptime
⚠️ Why not skip straight to Nexus for everything
Nexus OSS is more capable but has real ops overhead (JVM tuning, storage growth, upgrade cycles) — for a 60-person team that's mostly npm today, that's more surface area than the problem needs on day one. Start Verdaccio, migrate to Nexus only when a second ecosystem (Python, Docker) actually shows up.
POC SCAN SETUP — TRIVY + POLICY GATE
The fastest path to a working "no known vulnerabilities" guarantee: Trivy scans on cache-miss, blocks on Critical/High
Trivy is free, open-source, checks against multiple CVE feeds (NVD, GHSA, OSV), and runs in under a second per package for typical npm packages. No infrastructure beyond a CLI binary in your registry's fetch hook.

BUILD PLAN — PHASED ROLLOUT
PHASE 1 — Registry POC, npm-only, one team (1 Week)
Goal: Prove the proxy-cache loop works, near-zero cost.
Build
  • Deploy Verdaccio via Docker on an internal server/VM
  • Configure npmjs.org uplink + storage volume
  • Shared auth token, pilot team .npmrc pointed at it
  • Confirm proxy + cache works for real installs
Validate
  • Pilot team's normal npm install/CI still works unchanged
  • Second install of same package served from cache, not upstream
  • No noticeable slowdown vs. hitting npmjs directly
PHASE 2 — Trivy Scan Gate + Blocking (1-2 Weeks)
Goal: Vulnerable versions never reach a developer.
Build
  • Write scan-gate service implementing ScanProvider (Trivy)
  • Wire it into Verdaccio's on-fetch hook
  • policy.json with block-on Critical/High
  • Manual exception path (Slack message + config edit)
Validate
  • Install a known-CVE test package → confirm 403 block
  • Install its patched version → confirm it's allowed
  • Blocked-install error message is clear enough to self-serve
PHASE 3 — Nightly Rescan + Org-Wide Rollout (2-3 Weeks)
Goal: Every team on it, newly-disclosed CVEs caught retroactively.
Build
  • Nightly cron rescans all cached versions against fresh CVE feeds
  • Auto-quarantine + Slack alert on newly-flagged packages
  • Roll .npmrc config to remaining teams
  • Internal @company/* scope for publishing shared libs
Validate
  • All teams installing exclusively through internal registry
  • Rescan job correctly catches a simulated new CVE disclosure
  • No team reports being blocked without a clear resolution path
PHASE 4 — Multi-Ecosystem + Hardening (Ongoing)
Goal: Same guarantee for Python, Docker; tighten access control.
Build
  • Migrate to Nexus OSS (or add) for PyPI + Docker proxying
  • Same ScanProvider interface, add Grype for image scanning
  • SSO/LDAP auth, per-team scoped namespaces
  • Self-service exception request UI (small internal app)
Scale
  • License-compliance policy layer (block GPL/AGPL if required)
  • CI pipeline gate: builds fail on undeclared new vulnerable deps
  • Dashboard: org-wide usage, top offending packages, audit trail

Key insight: Phase 1 POC is intentionally simple — Verdaccio, npm only, no scanning yet. This proves the proxy-cache path works in about a week with zero licensing cost. The scan gate in Phase 2 is additive — the ScanProvider interface means swapping Trivy for OSV-Scanner or adding license checks later requires zero changes to the registry shell, just a new scanner module and a policy update.

Total to org-wide npm coverage with CVE blocking: ~4-6 weeks. Total to a working internal registry demo: ~1 week.
