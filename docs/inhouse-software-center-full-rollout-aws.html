AWS ARCHITECTURE — WHERE EVERY PIECE ACTUALLY RUNS
One VPC, one small EC2 instance for Phases 1-3, AWS-managed services added only where they remove real maintenance work
The tools themselves (Munki, Santa, Pi-hole) don't care what cloud they're on — this tab is the AWS-specific decision for each: what service hosts it, how it's reached securely, and where we deliberately use an AWS-managed service instead of running one more thing ourselves.

⚠️ AWS-managed pieces are added only where they buy something real
RDS/ElastiCache/Fargate/Lambda all cost more per hour than "just run it on the box" — the trade is real: each one removes a specific line from the Unknown Costs list (patching, backups, uptime babysitting) in exchange for a small, predictable AWS bill. Phases 1-3 deliberately stay on a single EC2 box because that trade isn't worth it yet at 8-10 pilot Macs.
PHASE 1 — VISIBILITY POC (WEEK 1)
Goal: full visibility into what's actually installed and running, with zero blocking
Everything here is observation-only. Nothing in this phase can break a real workflow — that's deliberate, so the pilot team has zero reason to distrust what comes next.

Exit criteria for Phase 1
  • Every pilot Mac has checked into Munki at least once
  • A full week of Santa Monitor logs reviewed, nothing unexplained left
  • Pi-hole confirmed blocking a real test domain, not just installed
What could go wrong here, specifically
  • Pilot Macs on a VPN that already forces DNS elsewhere — will silently bypass Pi-hole
  • ACM cert validation stalls if Route 53 DNS records aren't propagated first
  • Session Manager needs the SSM agent pre-installed on the AMI — check before relying on it

PHASE 3 — LOCKDOWN + ORG-WIDE ROLLOUT (WEEKS 4-6)
Goal: unsigned/unapproved binaries actually stop running — the real fix for the incident — without breaking everyday developer tooling
This phase only starts once Phase 1's Monitor logs have been read end to end. The single biggest risk here isn't the incident category (crack tools) — it's blocking legitimate Homebrew/CLI tools that were never signed in the first place. That risk gets a dedicated build step below, not an afterthought.
TaskOwner actionDone when
Clear the Monitor backlogAdd certificate allow-rules for every legitimate signed app seen in a week of logsNo unexplained unrecognized binary remains in the log
Enable compiler rulesEnableTransitiveRules = true; add ALLOWLIST_COMPILER rules for Xcode's linker, Go, and Homebrew's own binaryA local go build and a source-built brew formula both run without a block
Deploy the Homebrew hash-rule jobLambda + EventBridge (every 30 min): pull known-good SHA-256 hashes for common formulas from Homebrew's own metadata, push as Santa Binary rulesA fresh brew install jq runs on first launch, no block, no manual rule added
Flip pilot to LockdownClientMode = 2 pushed to the pilot group only, firstA real (harmless) unsigned test binary is blocked with the correct dialog
Roll to remaining MacsSame Munki + Santa + Pi-hole bootstrap, one team at a time, not all at onceEvery company Mac reports Lockdown mode active
Rollout order — don't do it all at once
  • Pilot group first, held at Lockdown for at least 3 working days before expanding
  • Engineering next (heaviest Homebrew/CLI usage — the compiler/package rules get their real test here)
  • Everyone else last — by this point the exception process has already been exercised
Rollback plan if something breaks
  • Per-machine: santactl can flip a single Mac back to Monitor mode immediately, by design
  • Fleet-wide (Phase 4+): a DDM declaration can revert ClientMode without visiting machines
  • Every rollback is logged as an incident of its own — a pattern of rollbacks means the rule set isn't ready, not that Lockdown is wrong

⚠️ Fleet's DDM channel is what makes "ongoing" actually sustainable
Every phase before this one assumed someone could reasonably touch each pilot Mac by hand. That stops being true past ~15-20 machines. Fleet Free's confirmed-free DDM support is what turns "push a Santa rule change" from a per-laptop task into a five-minute change that reaches the whole fleet — this is the phase where that capability actually gets used, not just planned for.
OWNERSHIP — WHO ACTUALLY RUNS THIS AFTER IT'S BUILT

⚠️ This plan assumes one person, part-time — that's a real constraint to say out loud
None of the above is full-time work at 60 people. But it is real, ongoing work that competes with whatever else that person is doing. If nobody is explicitly given a few hours a month for this, rule curation is exactly the kind of task that silently stops happening — and the whole plan's value depends on it not stopping.
POLICY & LEGAL — THE NON-TECHNICAL HALF OF THIS PLAN
Every tool in this plan logs employee activity — that needs a policy, a notice, and (separately) a response to the incident that already happened
This whole plan up to this tab is technical controls. None of it addresses updating what employees are told, or what happens with the specific incident that triggered this project in the first place. Both are real gaps a CEO is likely to ask about.
📋 Acceptable Use Policy update
  • Add an explicit clause: company devices run required security software (Santa, Munki, Pi-hole/DNS filtering)
  • State plainly that unauthorized/pirated software is prohibited — not assumed
  • Communicate before Lockdown mode goes org-wide, not after — this is what makes it feel like policy, not surveillance
🔒 Privacy notice for what's actually logged
  • Santa logs: binary name, path, signing status, allow/block decision — not file contents
  • Pi-hole logs: domains queried, not page content or search terms within a page
  • Fleet (Phase 4) logs: installed software inventory, not personal files or browsing history
  • Suggested retention: 90 days for routine logs, longer only when actively investigating an incident
THE ORIGINAL INCIDENT — SEPARATE FROM THIS PREVENTIVE PROJECT
Nothing in this rollout plan addresses the specific machine and vendor notice that already exist. That needs its own short, parallel track: identify the affected machine, run a malware scan (keygens commonly bundle infostealers — treat this as a possible compromise, not just a licensing issue), involve legal on how to respond to the vendor's notice, and decide separately whether any employee conversation is warranted. This plan prevents a repeat — it doesn't close the incident that's already open.
